# SWE-CI: agents maintaining a codebase over many changes

**In one sentence:** passing today's tests says little about maintainability; it shows up only across successive
changes, and on that measure current models regress often and write code that is tidy on the surface but more
complex than human code.

## Claim

Snapshot benchmarks (one requirement, one solution) cannot tell a brittle fix from an extensible one, because both
pass the same tests. The difference appears only when the codebase must keep evolving and earlier decisions
compound. The benchmark therefore measures functional correctness on *future* changes, with later iterations
weighted more heavily (the EvoScore).

## Evidence

Setting: 100 tasks from 68 Python repositories. Each task spans a real base commit and target commit, on average
233 days and 71 commits apart, with at least 500 changed source lines. An "architect" agent reads failing tests and
writes at most five behaviour-level requirements; a "programmer" agent implements them, may not edit tests and may
not run them. Up to 20 iterations; 20 models from 8 providers; more than 10 billion tokens.

- **Regressions are the main failure.** Most models finish with no regression in fewer than 25% of tasks. Only two
  exceed 50%: Claude Opus 4.5 at 51% and Claude Opus 4.6 at 76%.
- **Regressions become more frequent as iterations go on** for 12 of 20 models, while each one breaks a smaller part
  of the test suite.
- **Surface style is not maintainability.** On solved problems, 15 of 20 models beat the human code on Pylint
  (style and naming conventions). All 20 lose on the maintainability index, which is driven by cyclomatic
  complexity.
- **Smaller patches, worse structure.** Every model changed fewer lines than the human solution. The authors read the
  extra human lines as investment in abstraction, encapsulation and modularisation.
- **More turns do not compensate for capability.** Weaker models use up the 20-turn budget without finishing; most
  gains come in the first four turns.
- Most models solve fewer than half of all requirements by the end; Claude Opus 4.6 solves 91%.

## Adopted

- **Complexity ratchet** (`CONSTITUTION.md` section 3): a complexity limit whose grandfathered exemptions may only be
  removed. Lint and type checks alone would pass exactly the code this paper finds degrades. The ruff `C90` and
  ESLint `complexity` recipe, once in the shared template, now lives in the stack template, and the adoption skill
  uses it as an example.
- **Velocity defined as work that stays finished** (`CONSTITUTION.md` section 1), with change fail rate and change
  effort among its signals.

## Not adopted

- **A coding rule that code is designed for its expected life rather than patched minimally**, although minimal
  patches measurably cost maintainability. It is a coding preference, not a team agreement, so the shared kit leaves it
  to each person's own setup.
- The maintainability index itself. Measuring it needs radon, a new dependency; cyclomatic complexity, one of its
  main inputs, is already checked by tools the template has.
- The architect/programmer split as a required workflow. It resembles the spec-kit flow, but the
  benchmark forbids the programmer from running tests, which the kit would never do in practice.
- A rule that agents may not edit tests to make them pass. The benchmark enforces it; the kit does not state it.
  Worth considering as an agreement.

## Limits

- Python only, with pytest suites as the oracle; repositories filtered for 500+ stars and three years of
  maintenance.
- The maintainability index is a coarse metric, and the comparison to human code covers solved problems only.
- A benchmark of models, not an intervention study: it does not show which practices reduce regressions.
- Three of the five authors are from Alibaba Group, whose Qwen models are among those evaluated.
