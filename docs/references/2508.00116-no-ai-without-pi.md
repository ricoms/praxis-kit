# Process intelligence: AI grounded in an object-centric event log

**In one sentence:** AI improves an organisation's end-to-end processes only when it is grounded in those processes'
event data, and object-centric process mining is the way to build that grounding.

## Claim

AI today automates single tasks but rarely improves end-to-end processes, because it has no access to how the work
actually flows. The author compares this to the smartphone, which changed the edges of work more than its core.

Process mining builds process models from event logs, checks conformance against them and analyses performance.
Traditional process mining forces every event into one *case*, such as one order. That fails when one event
touches several objects. **Object-centric process mining** (OCPM) uses event data in which an event can refer to
several objects of different types, stored in the OCEL 2.0 format. **Process intelligence** (PI) is the author's
name for "process-centric data-driven techniques able to deal with a variety of object and event types, enabling AI
in an organizational context".

The paper names five ways the two combine:

1. Turn a process problem, such as a bottleneck, into a prediction problem.
2. Prescriptive AI: choose actions under goals and constraints.
3. Classical optimisation and planning.
4. Natural-language questions about the event data, answered with retrieval rather than guessed.
5. Help with turning source-system data into object-centric event data.

## Evidence

- None measured. This is a position paper that describes and argues; it runs no experiment.
- It cites the author's group's PM-LLM-Benchmark, which by March 2025 had evaluated close to 100 LLMs on
  process-mining tasks. The paper reports only which model ranked first.
- It cites an earlier case study by the same group, which found that LLM answers from textually encoded process
  variants are "not very reliable".
- The illustrations are screenshots from Celonis, the author's second affiliation.

## Adopted

Nothing yet. One radar entry at Assess, "Object-centric event log of the delivery lifecycle", takes up the idea.

Software delivery is object-centric by nature. One PR closes several issues, one release carries many PRs, and one
image digest is promoted through several environments. Three of the velocity signals in `CONSTITUTION.md` §1 have
no measure in the kit: change fail rate, rework rate and recovery time. All three are questions about an
object-centric event log of the delivery lifecycle, built from issues, PRs, CI runs, releases and deployment
records. `reading-delivery-velocity` measures waiting and effort from the board alone, which is a case-centric
version of the same idea.

The kit's required checks test one change at the gate. Conformance
checking would test the observed history instead, for example how many one-way PRs merged without an ADR in a
quarter. Agreements such as "a decision lives where it can be found" are what make that history observable.

## Not adopted

- **Process intelligence as a product category.** The kit adds no process-mining platform. If the event log is
  tried, it starts as a script over the GitHub API and the deployment records.
- **Measures per person.** `CONSTITUTION.md` §1 compares a team only with its own past, and no signal is a target.
  A log of per-person events would break that. The paper lists the resistance that process transparency causes as
  an adoption barrier but does not resolve it.
- **Prescriptive AI choosing actions.** In the kit, agents act for a named person and a correction narrows their
  scope. Actions chosen by an optimiser have no owner in that model.

## Limits

- The paper studies enterprise operations such as orders, invoices and deliveries, not software delivery. Process
  mining applied to software repositories has its own literature, which this note's author did not read.
- No evaluation, and the author has a commercial interest in the approach. The paper can frame the work. Under
  `CONSTITUTION.md` §7 it cannot serve as the evidence for an amendment.
