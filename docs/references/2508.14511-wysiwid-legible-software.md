# WYSIWID: concepts and synchronizations

**In one sentence:** structuring code as fully independent *concepts* coordinated only by declarative
*synchronizations* makes behaviour legible, keeps changes local, and lets an LLM generate each piece from a small
context.

## Claim

Code today is illegible (no direct mapping from code to observed behaviour) and insufficiently modular. That breaks
three properties coding needs, from humans and LLMs alike: **incrementality** (small changes stay local),
**integrity** (new changes do not break old behaviour) and **transparency** (it is clear what changed at build time
and what happened at runtime).

The pattern has two elements:

- A **concept** is a user-facing unit of functionality with one purpose, for example Password, Upvote or Profile.
  It has its own state and actions, and is specified with a purpose, state, actions and an *operational principle*
  (an archetypal scenario that also seeds tests). Concepts never call each other or read each other's state.
  References to other concepts' objects are opaque, polymorphic identifiers.
- A **synchronization** is a rule of the form *when* these actions happened, *where* the state is such, *then*
  invoke these actions. All cross-concept behaviour, including authentication, error handling and response
  assembly, is a synchronization. An incoming HTTP request is modelled as an action of a bootstrap "Web" concept.

## Evidence

- One case study: the RealWorld "Conduit" blogging backend, first written by hand, then regenerated by an LLM with
  the context limited to one concept's specification (for concept code) or to concept specifications only (for
  synchronizations). Concept generation "almost completed successfully in a single shot"; synchronizations needed
  iteration against the Postman test suite.
- A debugging story: a registration bug was found by querying the provenance graph for one request's flow and
  giving only the matching synchronizations to an LLM. The fix added two synchronizations and changed one, without
  touching other behaviour.
- Three existing RealWorld implementations were inspected and found to break their own layering rules (controllers
  bypassing models, reaching into other entities' models).
- No quantitative comparison. The authors say a systematic comparison has not been done.

## Adopted

- Concept-first decomposition by user-facing purpose, opaque ids across boundaries, cross-concept flows in
  `syncs/` written as trigger → condition → effect, and the legibility test (a feature is understood by reading its
  concepts and syncs). These live in the `CONSTITUTION.md` §4 practice below and in the project `CLAUDE.md`'s
  Modules and Flows sections that the shared template renders.
- In `CONSTITUTION.md` this becomes the practice "modules split by user-facing purpose, with flows between them kept
  explicit", switched on from `build` and applied to new code only in `sustain`.

## Not adopted

- **The paper forbids any call between concepts; the kit allows calls through public interfaces.** The paper also
  has no getters: reads go through queries in a synchronization's *where* clause. The kit's rule ("public
  interfaces only") is weaker. Whether to tighten it is an open question.
- The synchronization DSL and the engine that runs it, including flow tokens and provenance records. The kit's syncs
  are ordinary modules.
- RDF and SPARQL storage, URI naming and versioned named graphs. These are the authors' implementation choices, not
  part of the pattern.
- Operational principles as a required part of each concept specification. They would fit the spec-kit flow and the
  test tiers, and have not been tried.

## Limits

- One small application, built by the authors. No measurement of maintainability, defect rates or LLM success rates
  against a baseline.
- The authors report a cost: synchronizations are very granular, so the full context of a chain of actions is hard
  to see at a glance.
- The pattern builds on long-standing ideas, and the paper cites them: Parnas's information hiding and "uses"
  relation, coupling and cohesion, Sullivan and Notkin's mediators (which synchronizations closely resemble),
  aspect-oriented programming and domain-driven design aggregates. The novelty is the strictness of the
  independence rule, the declarative synchronizations, and the framing around LLM generation.
