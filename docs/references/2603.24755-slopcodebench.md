# SlopCodeBench: how agent-written code decays as it is extended

**In one sentence:** when coding agents keep extending their own solution, the code gets more complex and more
verbose with almost every step, more than human code does over its git history, and asking the agent to write cleanly
slows the decay without stopping it.

## Claim

A single-shot benchmark cannot show what happens to code that keeps changing. Quality has to be measured across
successive extensions of the same solution, with two composite scores that can be computed from the code alone:
structural erosion and verbosity.

## Evidence

Setting: 36 problems with 196 checkpoints, where an agent extends its own solution from one checkpoint to the next.
15 models from six providers, including Claude Opus 4.5 to 4.7 and GPT 5.x Codex models. Python only.

- **No agent solves a problem end to end.** The best passes 14.8% of checkpoints.
- **Quality decays along the way.** Structural erosion rises in 77% of trajectories and verbosity in 75.5%.
- **Against human code.** A sample of 473 Python repositories, up to 30 source-modifying commits each (13,667
  commits) across star tiers from hobby to major projects, averages 0.19 verbosity and 0.34 erosion at HEAD. Agent
  checkpoints average 0.44 and 0.68: 2.3 times more verbose and 2.0 times more eroded. Agent code also degrades more
  often and more steeply than the human repositories' git histories.
- **Prompting helps but does not hold.** An "anti-slop" prompt reduces verbosity by up to 34.8% and erosion by up to
  62.3% at first, but the decay continues. It costs 2.3 points of correctness and 12.1% more per checkpoint on average.

The two scores:

- **Structural erosion** is the share of a codebase's complexity mass that sits in functions above cyclomatic
  complexity 10, where a function's mass is its cyclomatic complexity times the square root of its source lines. One
  number per codebase, between 0 and 1.
- **Verbosity** is the share of source lines flagged by clone detection, 137 `ast-grep` rules for wasteful patterns, or
  structural rules. The rules cover Python; other languages contribute clone lines only.

## Adopted

- **Structural signals tracked over time, not surface lint.** The paper agrees with SWE-CI: surface checks pass code
  whose structure is decaying. It supports the complexity ratchet (`CONSTITUTION.md` section 3) and the code-health
  direction in `docs/adr/0001-kit-tooling-hugin.md`.
- **Erosion and verbosity as candidate signals** for `hugin`'s code-health analysis. Both are built from per-function
  complexity, size, clones and `ast-grep` rules, which are the inputs `hugin` is already choosing tools for.

## Not adopted

- **`scb-check` as a dependency.** It fails the adoption test in ADR 0001: one maintainer, created in April 2026, last
  released in May 2026. Its Apache-2.0 licence allows adapting its rules with attribution.
- **The threshold of 10** as a fixed fact. It is radon's convention, not something the paper derives. `hugin`'s
  conventions file records whichever threshold the kit chooses.
- **The 2.3 and 2.0 ratios as targets.** They compare fresh benchmark code with mature repositories, so they show
  direction, not a level a team should aim for.

## Limits

- Python only, in 36 constructed problems, with no human review between checkpoints. A team with review, CI gates and
  small changes is not in the setting.
- The human comparison is not like-for-like: different tasks, and repositories shaped over years.
- Like every structural measure, erosion and verbosity say nothing about whether the code is right for its users.
- This note's author read the HTML full text through a summary of its definitions and results, not the appendices or
  the per-model tables.
